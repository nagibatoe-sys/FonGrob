# Задание для Codex — вкладка «Пари»

Ты работаешь в существующем проекте. Реализуй вкладку «Пари» и экран создания пари максимально точно по приложенному prototype.html и screenshots/*.png. HTML — эталон разметки, текстов, размеров, цветов и интерактивного поведения, PNG — визуальные эталоны. Не заменяй их собственной концепцией. Сначала изучи структуру репозитория, AGENTS.md, стек, маршруты, авторизацию, дизайн-систему, API, модели данных и тесты. Используй существующий стек; не создавай отдельное приложение, не ломай соседние вкладки. Если есть конфликт между эталоном и существующим приложением, сохрани визуальную компоновку конструктора, интегрируй общую навигацию проекта и явно перечисли отличия. Не добавляй денежные ставки или платежи.

## Интерфейс
- Десктоп: область до 1248 px, две колонки 1.15:1, промежуток 24 px; слева форма, справа закрепляемый предпросмотр. Светлый фон #f7f7fa, белые панели, акцент #8263df, основные кнопки #7655cc, скругления 9–16 px. Сверяйся с CSS эталона. На ширине до 760 px — одна колонка без горизонтального скролла.
- Заголовок «Создание пари», хлебные крошки «Пари / Создание пари». Разделы «01. Формат пари», «02. Условия пари», «03. Настройки участия». Навигацию подключи к реальным существующим маршрутам; не делай фиктивных кнопок.
- Три карточки выбора формата, ровно одна активна. При переключении сохраняй черновики названия/условий каждого формата, сбрасывай ответ предпросмотра. Общие настройки сохраняются при переключении.
- Да / Нет: название, условия, дата события, два фиксированных ответа «Да», «Нет», без возможности редактирования вариантов.
- Варианты ответа: название, условия, редактируемый список минимум из двух ответов, кнопки добавления и удаления. Не разрешай пустые и дублирующиеся варианты (сравнение после trim без учёта регистра). Используй стабильные идентификаторы вариантов.
- Свободный ответ: название и условия, без списка вариантов; участнику доступно текстовое поле. Не разрешай пустые ответы.
- Во всех форматах обязательны дата и время «Приём ответов до». Дедлайн должен быть в будущем при публикации; для бинарного формата не позже конца даты события в часовом поясе пари. Отображай часовой пояс явно; храни время в UTC, а календарную дату события отдельно. Не смешивай дату события с дедлайном. Скрытые ответы — доступный с клавиатуры переключатель, включён по умолчанию. Если включён, ответы других участников и агрегаты недоступны до дедлайна, включая API; собственный ответ доступен. Если выключен — ответы доступны сразу в пределах прав просмотра пари.
- Предпросмотр обновляется без перезагрузки. Все три вида ответа интерактивны; кнопка «Отправить ответ» в предпросмотре проверяет значение и показывает явное демо-подтверждение, но не отправляет реальный ответ. Демо-ответ можно изменить. «Сбросить» возвращает форму к исходному состоянию; при потере введённых данных запроси подтверждение. «Создать пари» реально публикует валидное пари через API, защищена от двойной отправки; отображает загрузку, ошибку без потери формы и успешный переход к созданному пари. В рабочем приложении поля нового пари пустые, демонстрационные значения только для тестов/историй.

## Данные и сервер
Адаптируй схему к имеющимся моделям. Минимально: Pari(id, creatorId, type: binary|multi|free, title, condition, eventDate nullable, deadlineAt, timezone, hiddenAnswers, status, createdAt); PariOption(id, pariId, label, position); PariAnswer(id, pariId, userId, optionId nullable, freeText nullable, createdAt); уникальность pariId+userId. Статусы: draft, open, awaiting_result, completed. При наступлении deadlineAt (serverNow >= deadlineAt) запрети новые ответы и раскрой скрытые ответы для авторизованных участников. Проверяй это на сервере при каждом запросе, не полагайся только на таймер браузера; используй существующий планировщик, если нужен для материализации статуса. При создании и отправке валидируй права, тип, принадлежность варианта, дедлайн и обязательные поля. Не доверяй клиентскому времени. Применяй транзакции/уникальные ограничения против двойной отправки. Экранируй пользовательский текст. Не возвращай скрытые ответы или агрегаты через API, кэш, HTML, сериализованные данные до дедлайна. По умолчанию один реальный ответ на участника без изменения; это предложенное правило, если проект уже имеет другое — согласуй с имеющейся логикой. Для завершения пари используй существующий механизм итогов; если его нет, добавь авторизованное ручное завершение создателем с фиксацией результата (для свободных ответов — текст результата, без автоматического субъективного сравнения).

## Проверка и критерии приёмки
1. Визуально сравни все четыре desktop-состояния со скриншотами, а также mobile; запусти браузерные скриншоты на 1440 px и 390 px. Не меняй порядок блоков и русские подписи. Допустимы различия системных календарей и шрифтов; навигация соответствует реальному приложению.
2. Проверь переключение трёх форматов, сохранение черновиков, ввод названия и условий, изменение дат и времени, добавление/удаление вариантов, минимум два, запрет дублей, оба состояния скрытых ответов, выбор Да/Нет и произвольного варианта, ввод текста, демо-отправку, изменение демо-ответа, сброс, публикацию, ошибки сервера и защиту от повторной отправки.
3. Проверь серверные права, граничный момент дедлайна, часовой пояс, отсутствие утечек скрытых ответов, смену статуса, завершение, сохранение после перезагрузки, отсутствие двойных ответов. Используй фиксированное тестовое время, а не даты примеров как актуальные.
4. Проверь доступность: видимые подписи, focus-visible, Tab/Enter/Space, aria-checked/aria-pressed, контраст, сообщения ошибок. Все отображаемые кнопки должны иметь реальную функцию или быть явно недоступны с объяснением. Не оставляй TODO, пустых обработчиков, фиктивных API или ложных сообщений успеха.
5. Запусти имеющиеся lint/typecheck/build/tests и добавь тесты для новой функции. В конце перечисли изменённые файлы, миграции, команды запуска, результаты проверок и реальные ограничения. Не заявляй о прохождении тестов, если не запускал их.

Выполни реализацию в репозитории, а не только опиши план. prototype.html является независимым демонстрационным эталоном: создание и отправка в нём локальные, серверное поведение необходимо реализовать в проекте. При отсутствии доступа к серверной части явно обозначь блокер вместо имитации сохранения.
